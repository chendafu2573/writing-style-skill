# 场景化写作规则

> 先选场景，再套规则。不同场景不能共用同一套情绪和结尾。

## 场景总表

| 场景 | 先写什么 | 必须分开 | 不要套用 |
|---|---|---|---|
| 项目争议 | 具体损失、规则变化、谁负责 | 个人经历 / 群体结论 | 把个人遭遇写成全社区事实 |
| 市场播报 | 时间窗、数据、变化、判断 | 数据 / 推测 / 风险 | 用情绪代替数据 |
| 产品评测 | 亲自使用、操作结果、缺点 | 功能 / 体验 / 长期价值 | 只写“值得关注” |
| 游戏体验 | 玩了什么、花了什么、得到什么 | 一次体验 / 普遍规律 | 把一次收益写成稳定收益 |
| 个人吐槽 | 真实导火索、情绪、最后判断 | 愤怒 / 事实 / 推测 | 为了整齐补总结和鸡汤 |

## 规范名称和别名

规范名称只有上表五类：`项目争议`、`市场播报`、`产品评测`、`游戏体验`、`个人吐槽`。

| 旧称或输入说法 | 规范场景 |
|---|---|
| 工具实测、工具推荐 | 产品评测 |
| 经验复盘 | 根据内容归到项目争议、产品评测或游戏体验 |
| 项目分析 | 根据是否有争议归到项目争议或产品评测 |

一个样本可以有一个主场景和零到两个辅助标签。主场景决定结尾和事实边界，辅助标签只补充规则，不能覆盖主场景。

混合内容默认选择信息量最大的主线；无法判断时标记 `scene: 未确认`，只用全局保护规则，不套用项目争议的情绪推进，也不把产品体验写成市场事实。

## 项目争议

- 开头从损失、规则变化或亲身经历进入。素材里已有玩家处境时，先写自己人被怎么对待，再补玩法、规则和责任人。
- 保留愤怒、重复、反问和口语，但必须有具体行为支撑。
- 明确“我经历的”“我看到的”“项目方公开说的”。
- 结尾可以落到责任、赔付、等待或最后一个未解决的问题。

## 市场播报

- 每组数据带时间窗和来源口径。
- 事实、计算结果、个人推测分开写。
- 不把成交量直接等同于产品成功。
- 结尾优先给验证条件，不用“未来可期”。

## 产品评测

- 先写实际怎么用，再写为什么顺手或难用。
- 缺点和限制不能被“整体不错”盖掉。
- 功能存在不等于用户会长期使用。
- 结尾写适合谁、不适合谁，或留下一个待验证问题。

## 游戏体验

- 保留操作、投入、收益、损失和当时动机。
- “我玩到的”不能升级成“玩家普遍”。
- 单次空投、积分或收益只代表一次结果。
- 结尾保留作者自己的判断，不补行业总结。

## 个人吐槽

- 保留自然重复和不规则节奏。
- 不强行把情绪整理成三段式论证。
- 不为了“像人”凭空添加脏话、夸张或反问。
- 最后停在事实、冷幽默、边界或一句仍然不爽的话上。

## 指定仿写口吻

作者说「XX 口吻」时，读取 `reference/voices.md`（仿写口吻库）；口吻不是场景，场景照常判断。

## 共同边界

```text
如果是用户完整原稿：先保护，再诊断。
如果是 Agent 初稿：用户改回的内容不能当作成功偏好。
如果是动态数据：记录时间窗，定稿前回看来源。
如果是个人口语：有经历支撑就保留。
如果是抽象金句：先检查是否压扁了原判断。
```
